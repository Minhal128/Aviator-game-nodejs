Ludo Royale · Documentation

Welcome

Ludo Royale is a real-time multiplayer Ludo game with a server-authoritative Colyseus backend and an optional POWER Mode — collectible board power-ups plus a shop of gold-bought battle powers — layered on top of classic Ludo rules. This single-page guide covers everything you need to run it locally, deploy it to your own server, and customize it for your brand.

What you're getting Full TypeScript source for three packages — shared (the rules engine), client (the Phaser 4 game), and server (the Colyseus + Express backend) — plus 249 automated tests and this documentation. There is no bundled admin panel in v1.0; all tuning is done through the lr_settings database table (see Economy & Tuning).

The compiled client/ web build is static HTML/CSS/JS and can be hosted anywhere, including shared hosting, as long as it can reach a game server you host elsewhere.

Monorepo layout

ludo-royale/
├── shared/   @ludo/shared   — pure TypeScript Ludo rules engine + AI (no Phaser, no network)
├── client/   @ludo/client   — Phaser 4 game client (web, PWA-installable)
└── server/   @ludo/server   — Colyseus game server + REST API (two processes, one codebase)

shared is the single source of truth for the rules. Both the offline driver (vs CPU / Pasa y Juega, played entirely in the browser) and the authoritative Colyseus server run the exact same compiled reducer — there is zero rule divergence between offline and online play, and it is covered by 133 of the project's 249 tests.

Getting Started

Quick Start — Local

Everything below runs on your own machine (Windows, macOS or Linux) with Node 22 and a local MySQL/MariaDB instance. Total time: about ten minutes.

1. Install dependencies

From the root of the extracted product folder:

npm install

This installs all three workspaces (shared, client, server) in one pass.

2. Build the rules engine

The server imports @ludo/shared as a regular npm package (resolved from its compiled dist/ folder), so it must be built once before the server will start. The client does not need this step — it consumes the shared TypeScript source directly through a Vite alias. 

npm run build:shared
Re-run after editing shared/ If you customize any file under shared/src/ (rules, constants, AI), re-run npm run build:shared so the server picks up the change. The client picks up shared/src changes instantly via hot reload — no rebuild needed there.

3. Create the database

Create an empty MySQL 8 (or MariaDB 10.6+) database and a user that can read/write it:

CREATE DATABASE ludo_royale CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'ludo'@'localhost' IDENTIFIED BY 'a-local-password';
GRANT ALL PRIVILEGES ON ludo_royale.* TO 'ludo'@'localhost';
FLUSH PRIVILEGES;

4. Configure environment variables

Copy the example files and fill them in:

cp server/.env.example server/.env
cp client/.env.example client/.env

Open server/.env and set at minimum:

VariableLocal value
DATABASE_URLmysql://ludo:a-local-password@127.0.0.1:3306/ludo_royale
JWT_SECRETany random string ≥ 32 characters — see below

Generate a strong JWT_SECRET with either of these (no openssl needed on Windows):

node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
# or, if you have OpenSSL:
openssl rand -base64 48

client/.env can stay empty for local dev — the client defaults to ws://localhost:8107 automatically when VITE_GAME_WS is unset in dev mode.

5. Run migrations and seed core data

npm run db:migrate --workspace @ludo/server
npm run db:seed --workspace @ludo/server

Migrations create the full schema (settings, economy, matches, shop, social, wheel, mail, etc. — see Economy & Tuning for the settings table). The seed populates default settings, feature flags, the 50-level XP curve, the 7-day daily bonus calendar, emotes, room tiers, default missions and shop items. Both commands are idempotent — safe to re-run any time without duplicating or clobbering data.

6. Start the two server processes

The server package is one codebase, two processes: the Colyseus game server (real-time match state) and the Express REST API (auth, shop, missions, wallet, etc.). Run each in its own terminal: 

# terminal 1 — ludo-game (Colyseus, default port 8107)
npm run dev --workspace @ludo/server

# terminal 2 — ludo-api (REST API, default port 8110)
npm run api:dev --workspace @ludo/server

7. Start the client

# terminal 3
npm run dev --workspace @ludo/client

Open http://localhost:5173 — the game creates a guest account automatically on first load, no login screen required.

8. Run the test suite (optional but recommended)

npm test

Runs 249 tests total: 133 in shared (rules engine, AI, determinism between offline/online) and 116 in server (REST endpoints, wallet, matchmaking, reconnection, anti-cheat).

Getting Started

Production Deploy

Ludo Royale's server is two long-running Node processes plus a MySQL database, fronted by nginx. This section walks through a clean Ubuntu VPS deploy with PM2 and a real domain.

Server requirements

  • VPS: 2 vCPU / 2 GB RAM minimum, 4 GB recommended.
  • Ubuntu 22.04/24.04 (or any Linux distribution with systemd).
  • Node.js 22 LTS, MySQL 8 or MariaDB 10.6+, nginx.
  • A domain with DNS pointed at the VPS (SSL via Let's Encrypt / certbot).
Not supported Shared hosting / cPanel cannot run two persistent Node processes and proxy a WebSocket upgrade — the server/ package needs a VPS or equivalent. The compiled client/dist/ web build is static and can be hosted anywhere, including shared hosting, as long as it can reach a game server hosted elsewhere.

1. Domain layout

This build's client connects to the Colyseus game server at the same origin it is served from by default (no /path prefix — see client/src/game/net/config.ts). Because the game process speaks WebSocket-only with no separate router in front of it, the simplest and most robust production layout uses two subdomains: one for the site (static client + REST API) and one dedicated to the game server. This avoids any ambiguity in nginx about which paths belong to which backend.

SubdomainServesProxies to
yourdomain.comStatic client (client/dist/) + /api/*ludo-api on 127.0.0.1:3000
ws.yourdomain.comColyseus matchmaking + WebSocket upgradeludo-game on 127.0.0.1:8107

If you'd rather use one domain only, that also works: skip the ws. subdomain, point VITE_GAME_WS at a different port on the same host instead (e.g. wss://yourdomain.com:8443) and open that port through your firewall / SSL termination. The two-subdomain layout below is the path of least resistance with a single nginx + certbot setup.

Deployment architecture at a glance

Both Node processes read the same server/.env, live behind nginx on localhost-only ports, and share one MySQL database. The build pipeline is: npm run build:shared → build server → build client (with VITE_GAME_WS pointing at the ws. subdomain) → copy nothing anywhere: nginx serves client/dist in place.

2. Get the code onto the server and install

cd /var/www
git clone <your private copy of the source> ludo-royale   # or scp/rsync the extracted ZIP
cd ludo-royale
npm ci

3. Build all three packages

npm run build:shared
npm run build --workspace @ludo/server
npm run build --workspace @ludo/client

This produces shared/dist, server/dist (both entrypoints) and client/dist (the static site).

4. Configure environment variables

cp server/.env.example server/.env
cp client/.env.example client/.env

Edit server/.env:

VariableProduction value
GAME_PORT8107 (internal — nginx is the only thing that reaches it)
GAME_HOST127.0.0.1
API_PORT3000
API_HOST127.0.0.1
DATABASE_URLmysql://ludo:•••@127.0.0.1:3306/ludo_royale
JWT_SECRETrandom string ≥ 32 chars — node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
ALLOWED_ORIGINSleave unset — see the callout below
Set DATABASE_URL for BOTH processes ludo-game boots and plays matches even without DATABASE_URL — but with no persistence and prizes forced to 0 (a deliberate dev-mode fallback, logged loudly on start). Make sure server/.env is readable by both the ludo-api and ludo-game processes so this never happens by accident in production.
CORS / ALLOWED_ORIGINS with the two-subdomain layout The client calls /api/* relative to its own origin (yourdomain.com), so with the layout above CORS stays same-origin and ALLOWED_ORIGINS can stay unset. Only set it if you serve the client from a third origin (e.g. a separate static host or CDN) that calls the API cross-origin.

Edit client/.env and set the game server subdomain before building the client — Vite bakes this value in at build time:

VITE_GAME_WS=wss://ws.yourdomain.com
Rebuild after changing client/.env VITE_GAME_WS (and any other VITE_* variable) is compiled into the static bundle. If you change it, you must re-run npm run build --workspace @ludo/client — restarting nginx or the server processes has no effect on an already-built client.

5. Migrate and seed the database

npm run db:migrate --workspace @ludo/server
npm run db:seed --workspace @ludo/server

6. Process manager — PM2 (recommended)

npm install -g pm2

Create ecosystem.config.cjs at the repo root:

module.exports = {
  apps: [
    {
      name: 'ludo-api',
      cwd: '/var/www/ludo-royale/server',
      script: 'dist/api.entry.js',
      instances: 1,
      max_memory_restart: '512M',
      env: { NODE_ENV: 'production' },
    },
    {
      name: 'ludo-game',
      cwd: '/var/www/ludo-royale/server',
      script: 'dist/game.entry.js',
      instances: 1,
      max_memory_restart: '768M',
      env: { NODE_ENV: 'production' },
    },
  ],
};

Both entrypoints read server/.env at boot (falling back to a repo-root .env if present), so you don't need to duplicate secrets into the PM2 env block above. 

pm2 start ecosystem.config.cjs
pm2 save
pm2 startup   # prints a systemd command to run once, so PM2 survives reboots

Alternative: systemd units

If you prefer systemd directly instead of PM2, two near-identical unit files work — one per process, each with WorkingDirectory=/var/www/ludo-royale/server, ExecStart=/usr/bin/node dist/api.entry.js (or dist/game.entry.js), Restart=on-failure, and User= a non-root service account.

7. nginx

Two server blocks, both behind certbot-managed SSL:

# /etc/nginx/sites-available/yourdomain.com
server {
  listen 443 ssl http2;
  server_name yourdomain.com;
  # certbot manages ssl_certificate / ssl_certificate_key here

  root /var/www/ludo-royale/client/dist;
  location / {
    try_files $uri /index.html;
  }

  location /api {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}

# /etc/nginx/sites-available/ws.yourdomain.com
server {
  listen 443 ssl http2;
  server_name ws.yourdomain.com;
  # certbot manages ssl_certificate / ssl_certificate_key here

  location / {
    proxy_pass http://127.0.0.1:8107;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_read_timeout 3600s;   # keep long-lived match connections alive
  }
}
sudo ln -s /etc/nginx/sites-available/yourdomain.com /etc/nginx/sites-enabled/
sudo ln -s /etc/nginx/sites-available/ws.yourdomain.com /etc/nginx/sites-enabled/
sudo certbot --nginx -d yourdomain.com -d ws.yourdomain.com
sudo nginx -t && sudo systemctl reload nginx

Firewall: only 80/443 need to be open to the world. 3000 and 8107 must stay bound to 127.0.0.1 — nginx is the only thing that should ever reach them.

8. Verify

  • curl https://yourdomain.com/api/health → {"ok":true,"db":true,...}
  • Open https://yourdomain.com in a browser, confirm a guest session starts and the home screen loads.
  • Start a Quick Match or vs CPU match and confirm the dice/board respond — this exercises the ws.yourdomain.com WebSocket path end to end.
  • pm2 logs should show ludo-game persistence enabled, not the "WITHOUT DATABASE_URL" warning.

Updating to a future version

  1. Pull/copy the new source over the old one (keep your server/.env and client/.env).
  2. Re-run step 3 (build all three packages).
  3. Run npm run db:migrate --workspace @ludo/server — new migrations are added as extra drizzle/000N_*.sql files and are safe to re-run.
  4. pm2 restart ludo-api ludo-game.
Game

Game Features

A tour of what ships in v1.0, grouped the way a player experiences it.

Ways to play

🌐

Quick Match

Real-time 2/3/4-player matchmaking, grouped by table size, tier and CLASSIC/POWER mode so queues never mix.

🔑

Private Rooms

Create a room, share the 6-character code, friends join with it. Host picks mode and player count.

🤖

vs CPU

3 AI difficulties (Easy/Medium/Hard). Medium and Hard AI seats are given battle powers too, so POWER matches against the CPU stay contested.

📱

Pasa y Juega

2–4 players on one device, passing turns — no account or network needed.

Core Ludo rules

  • Roll a 6 to leave base and to take an extra turn.
  • Landing on an opponent captures it back to base (star cells are safe — no captures there).
  • Three consecutive 6s in one turn forfeits the turn.
  • Configurable turn timer (default 15s) with auto-move on timeout, so idle players never stall a match.
  • All of the above lives in @ludo/shared and runs identically offline and online — see POWER Mode for the additional power-up layer.

Reconnection & anti-cheat

  • Dropped connections get a grace window to reconnect into the same seat (session token stored client-side) — the match keeps running with the seat on auto-play in the meantime.
  • The dice roll is generated server-side only; the client never decides an outcome. Every move is validated against the shared rules engine before the room state changes.
  • Abandoning a match counts as a forfeit and is scored accordingly on the leaderboard.

Communication in-match

  • Emote wheel — a set of default reaction emotes, broadcast to the table in real time.
  • Quick-chat phrases — six preset phrases ("Well played!", "Sorry mate!"...) sent the same way, no free-text chat (keeps moderation simple; a full world/free-text chat is intentionally out of scope for v1.0).

Progression & economy

🏅

XP & Levels

50-level curve, coin + gem rewards on level-up (see Economy & Tuning for the exact numbers).

🎁

Daily Bonus

7-day reward calendar with a streak — miss a day and the streak resets.

🎡

Lucky Wheel

Free spins per day (default 3), coin/gem prizes on a 6-segment wheel.

✅

Missions

Daily mission set (play matches, win, capture pieces, roll sixes, bring pieces home) with coin rewards.

🏆

Leaderboard

Score from wins/podiums/forfeits, with coin rewards for the top 3 each period.

👥

Friends & Invite

Friends list and a referral flow that rewards both sides once the invitee reaches a qualifying level.

Shop

Seven tabs, each a cosmetic or gameplay-adjacent purchase — nothing pay-to-win beyond the optional battle powers, which are capped per match (see POWER Mode). Buying a cosmetic (die, pawn, chat bubble or board theme) equips it automatically; the Backpack lets the player switch back to any owned skin or the classic default at any time:

TabWhat it sells
DiceDice skins (Gold, Mint, Ruby, Galaxy).
PawnsPiece skins layered over the base art.
Chat bubblesPalettes for the in-match quick-chat/emote bubble.
ThemesFull board re-skins.
PowersThe four battle powers — Trap Bomb, Bolt, Freeze, Portal — bought with coins.
CoinsGem → coin conversion packs.
GemsIAP placeholders — visible in the shop with the buy button disabled; wire up your own payment provider to enable them (no payment gateway is bundled).

Accounts

  • Guest-first — every session starts with an automatic guest account, no signup friction.
  • Upgrade to email — a guest can register an email + password at any time without losing coins, gems, level or inventory.
  • JWT-based sessions with refresh tokens.

Platform

  • Installable PWA — manifest + service worker included, "Add to Home Screen" on mobile and desktop browsers.
  • i18n — English and Spanish included out of the box (see Customization to add more).
  • Mobile-first, candy-style visuals — the entire board, pieces, dice and UI chrome are procedurally generated at boot; there are no binary board/piece assets to replace if you re-theme.
  • prefers-reduced-motion is honored — animations collapse to short fades while still conveying the result.
Not included in v1.0 There is no bundled admin/back-office panel and no payment gateway wired up (the gem packs are IAP placeholders — see the Shop table above). Tuning is done directly through the lr_settings database table; see Economy & Tuning.

POWER Mode

POWER Mode is the headline feature: any match (Quick Match, Private Room, vs CPU, or Pasa y Juega) can be started with Modo → POWER instead of Clásico. It layers eight power-ups — four that drop randomly on the board, four bought with gold in the shop — on top of standard Ludo rules, running through the exact same server-authoritative engine as classic matches.

The two power families

Classic (4)Battle (4)
How you get themDrop as collectible tokens on the board while playingBought with coins in the Shop → Poderes tab
Powers+1, Double Roll, Pick Dice, ShieldTrap Bomb, Bolt, Freeze, Portal
Per-match limitCharge cap of 3 per type (extra pickups past the cap are wasted)Cap of 2 uses of each per match, seeded from your shop inventory
Sold in the shop?No — board-onlyYes

Classic powers (board drops)

  • +1 — nudge one of your pieces forward a small extra step.
  • Double Roll — arms your next roll to be two dice combined instead of one.
  • Pick Dice — arms your next roll so you choose the face yourself instead of rolling.
  • Shield — protects one of your pieces on the board.

Token drop mechanics (tunable in shared/src/ludo/constants.ts — a shared-package rebuild is required after any change here, see Quick Start):

Constantv1.0 valueMeaning
POWER_INITIAL_TOKENS3Tokens on the board when the match starts.
POWER_MAX_TOKENS6Cap on tokens present at once.
POWER_SPAWN_PCT38%Chance a new token spawns after a roll (deterministic hash, not client RNG).
POWER_WEIGHTS+1: 40 · Double: 25 · Pick: 20 · Shield: 15Relative spawn odds — +1 is common, Shield is the rare one.
POWER_CHARGE_CAP3Max stored charges per classic power type.

Battle powers (shop, gold-bought)

  • 💣 Trap Bomb (1,000 coins) — plant a trap on a track cell; the next piece that lands on it triggers the trap. Rivals never see your trap marker — only you do, until it detonates.
  • ⚡ Bolt (1,200 coins) — knock an opponent's piece back 6 cells on the ring (past the start of their run, it goes all the way back to base).
  • 🧊 Freeze (1,000 coins) — lock down an opponent's piece on the board.
  • 🌀 Portal (1,500 coins) — teleport one of your own pieces forward.
Why the 2-per-match cap matters Buying a battle power grants inventory, but each match only seeds up to POWER_MATCH_CAP (2) charges of each type regardless of how many you own — so a wealthy player can't stack unlimited disruption in a single match. It's the same cap the AI uses: Medium bots start with 1 Bolt + 1 Freeze, Hard bots start with one of each of the four.

Where it shows up in the UI

  • Setup screens (Quick Match, Private Room, vs CPU, Pasa y Juega) all have a Clásico / POWER toggle.
  • In-match power rail — a row of icons above the action bar shows your current charges of all 8 power types; tap one to use it (targeting a cell or an enemy piece where applicable).
  • Shop → Poderes tab — buy battle-power charges with coins; "Tienes: ×N" shows your current owned stock.

Economy & Tuning

v1.0 has no admin panel, so balance changes are made directly against two database tables — no code change or rebuild required for most of them. This section lists every tunable value and exactly where it lives.

Two different places to tune things Database (lr_settings, lr_shop_items, lr_feature_flags, ...) — edit with any SQL client, takes effect immediately, no rebuild. Code (shared/src/ludo/constants.ts) — power-drop odds, AI weights, XP curve formula; editing these requires npm run build:shared and a restart of both server processes (see Quick Start).

lr_settings — key/value store

Read/write with plain SQL, e.g.:

UPDATE lr_settings SET value = '20' WHERE `key` = 'turn_timer_s';

lr_shop_items — prices & catalog

Every shop entry (dice/pawn/bubble/theme skins, battle powers, coin packs) is a row in lr_shop_items with priceCurrency, priceAmount, isFeatured and sortOrder columns — change a price or feature flag with a plain UPDATE, add a new cosmetic SKU with an INSERT (pair it with a matching assetKey the client bakery recognizes).

lr_feature_flags

A phased-rollout table (flag, enabled, phase). v1.0 ships with the full game unlocked; the table is there so you can stage your own roadmap the same way without a redeploy — flip a flag and gate your own client-side check on it if you add new features later.

XP curve & daily bonus (seed-time, not live-tunable)

The 50-level XP curve and the 7-day daily bonus calendar are written once by seedCore() into lr_xp_levels and lr_daily_bonus_config — both are plain tables, so you can also edit rows there directly with SQL after seeding; they are not re-seeded on subsequent db:seed runs (upsert is a no-op on existing keys).

Formula used at seed time: xpRequired = 50 × (level − 1) × level — level 2 = 100 XP, level 10 = 4,500 XP, level 50 = 122,500 XP. Reward: 100 × level coins per level-up, +5 gems every 5th level.

Code-level tuning (requires a rebuild)

These live in shared/src/ludo/constants.ts and are compiled into @ludo/shared — see the callout at the top of this section:

  • POWER_INITIAL_TOKENS, POWER_MAX_TOKENS, POWER_SPAWN_PCT, POWER_WEIGHTS, POWER_CHARGE_CAP — classic power drop mechanics.
  • POWER_PRICES, POWER_MATCH_CAP, BOLT_KNOCKBACK — battle power economy and effect strength.
  • AI_WEIGHTS, AI_POWER_LOADOUTS — CPU decision-making and starting power charges per difficulty.
Battle power prices exist in two places POWER_PRICES in constants.ts is what the shared engine expects when validating a purchase server-side; the coin amounts shown in the Shop UI come from lr_shop_items.priceAmount. If you change one, change the other to match, or a purchase can be rejected (or under/over-charged) by the server's validation.

Branding, i18n & PWA

What to touch to make Ludo Royale look and read like your own product.

Color palette (board, pieces, dice, HUD)

The board, dice, pieces and most HUD chrome are drawn procedurally at boot — there are no board/piece/dice image files to replace. Every color is a single named constant in client/src/theme/tokens.ts: 

export const LR_COLORS = {
  worldTop: 0x5e3fd6,       // primary violet (background gradient top)
  worldBottom: 0xc77de0,    // secondary (background gradient bottom)
  worldSpotlight: 0xb98bea,
  ...
};

export const LR_PLAYERS = {
  red:    { light: 0xff6b73, mid: 0xf5333f, dark: 0xc21521, tint: 0xfde7e8 },
  green:  { light: 0x5fe3a0, mid: 0x23c275, dark: 0x128a50, tint: 0xe4f8ee },
  yellow: { light: 0xffd75a, mid: 0xfbbf16, dark: 0xc98a00, tint: 0xfff6dc },
  blue:   { light: 0x6bb2ff, mid: 0x2d8cf5, dark: 0x175fbf, tint: 0xe3f0ff },
};

Change a value here and every baker (board, dice, pieces, particles, UI panels) re-paints from it automatically — no per-scene hunting for hardcoded hex values. Rebuild the client after any change (npm run build --workspace @ludo/client); in dev mode Vite hot-reloads it instantly.

Translations (i18n)

English and Spanish ship in client/src/i18n/en.ts and es.ts — flat key → string maps (357 keys each), consumed through t('some.key') everywhere in the client. The game starts in English by default; players can switch language from the in-game Settings panel (persisted in localStorage, so the choice sticks across visits).

To add a language (e.g. French):

  1. Copy en.ts to fr.ts and translate every value (keep the keys and any {placeholder} tokens identical).
  2. In client/src/i18n/index.ts, import it, add 'fr' to the Locale union, and add a branch in applyLocale().
  3. Add a way to select it from the Settings panel's language switcher.
Keep placeholders intact Strings with {param} tokens (e.g. countdown timers, prize amounts) are interpolated at runtime by t(key, params) — dropping or renaming a {token} in a translation leaves the literal placeholder text on screen instead of the value.

Product name & package metadata

Update name/description in the four package.json files (root, shared, client, server) and the manifest above. There is no separate "renaming" step — the codebase does not hardcode "Ludo Royale" anywhere that affects runtime behavior.

Rebrand Without Coding

A checklist for making the game yours without touching any game logic. Every step is either "replace an image file" or "edit a few words in a text file" — if you can rename files and use a text editor, you can do all of this. The only terminal command involved is the final rebuild.

Step 1 — Replace the art (no tools needed)

Open client/public/assets/art/. Every image the menus use is a plain PNG. Replace any of them with your own image, keeping the exact same filename and a similar shape:

emoji_01.png … emoji_08.pngThe reaction emotes players send in a match.
nav_*.pngThe six icons in the bottom navigation bar.

Step 2 — Rename the game (edit one text file)

Open client/public/manifest.webmanifest in any text editor and change the "name", "short_name" and "description" values. This renames the browser tab, the PWA install prompt and the home-screen icon label.

Step 3 — Change the two main colors (edit two lines)

Open client/src/theme/tokens.ts, find these two lines near the top, and swap in your brand colors (hex format, keeping the 0x prefix): 

worldTop: 0x5e3fd6,       // background gradient — top
worldBottom: 0xc77de0,    // background gradient — bottom

Every screen background, panel tint and particle color derives from the palette in this one file — there is nothing else to hunt down.

Step 4 — Replace the app icons (optional)

Drop your own icon-192.png and icon-512.png into client/public/icons/, then remove gen-icons.mjs from the dev/build lines in client/package.json so the build stops regenerating them (see Branding, i18n & PWA).

Step 5 — Rebuild (one command, or ask your developer)

npm run build --workspace @ludo/client
That's the whole rebrand Steps 1–4 are file edits anyone can do. If you are not comfortable running the build command, hand the folder to any developer — the rebuild takes under a minute and nothing else needs to change.
Changing texts? Every label, button and message lives in two dictionary files — client/src/i18n/en.ts (English) and es.ts (Spanish). Edit the text between the quotes on the right-hand side of each line; never change the key on the left. Rebuild afterwards.

Support

Troubleshooting & FAQ

The most common issues buyers hit, and the fix for each.

"ludo-api cannot boot — invalid environment"

The API process validates its environment with zod at startup and refuses to boot with a vague error otherwise. The message lists exactly which variable failed — the two most common causes:

  • JWT_SECRET shorter than 32 characters — generate a longer one (see Quick Start).
  • DATABASE_URL not starting with mysql:// — check for a stray Postgres-style URL or missing scheme.

Matches aren't saved / prizes are always 0

ludo-game boots fine without DATABASE_URL — on purpose, so local rules/AI development never needs a database — but it then runs in a no-persistence mode with prizes forced to 0, and logs a loud warning on start (ludo-game running WITHOUT DATABASE_URL). Set DATABASE_URL in server/.env and restart the process.

WebSocket connection fails / stuck on "Connecting…" in production

  • Check the nginx block for the game server has the WebSocket upgrade headers (Upgrade/Connection "upgrade") — see Production Deploy. A missing upgrade block is the #1 cause of a match that never connects.
  • Confirm ports 8107 (game) and 3000 (API) are not open to the public internet directly — only nginx (443) should be, and nginx should be proxying to 127.0.0.1.
  • If you're behind Cloudflare (proxied/orange-cloud), WebSockets are supported, but Cloudflare's own idle timeout is around 100 seconds — Colyseus' internal keepalive pings handle this automatically, so no extra config is needed, just don't disable it.
  • If you changed VITE_GAME_WS, remember it's baked in at build time — a plain server restart does not pick it up; rebuild the client.

CORS errors in the browser console

Only relevant if the client is served from a different origin than the API (e.g. a separate static host/CDN). Set ALLOWED_ORIGINS in server/.env to a comma-separated list of the exact origins allowed to call /api/*. Leave it unset for the standard same-origin nginx layout in Production Deploy.

"npm run dev --workspace @ludo/server" fails to resolve @ludo/shared

The server resolves @ludo/shared as a normal npm package pointed at its compiled dist/ folder (unlike the client, which aliases the TypeScript source directly). Run npm run build:shared once, and again any time you edit shared/src/.

A shop purchase is rejected or charges the wrong amount

Battle-power prices exist in two places that must agree: the coin amount shown in the Shop UI (lr_shop_items.priceAmount, DB-editable) and the amount the shared engine expects when validating the purchase server-side (POWER_PRICES in shared/src/ludo/constants.ts, requires a rebuild). See Economy & Tuning.

Re-running db:migrate / db:seed

Both are safe to run repeatedly. Migrations use CREATE TABLE IF NOT EXISTS; the seed upserts on natural keys and never overwrites a row that already exists (so admin-edited lr_settings/lr_shop_items values are never clobbered by re-seeding). New versions ship additional drizzle/000N_*.sql files that apply in filename order.

Running the test suite against a real database

The 116 server tests that touch the database (files named *.db.test.ts) need a separate DATABASE_URL_TEST database — they TRUNCATE every lr_ table between test cases. Never point it at a database with real data. The 133 shared tests need no database at all (pure rules engine + AI).

Guest account lost its coins/level

Guest accounts are identified by a token stored in the browser (localStorage/IndexedDB). Clearing site data, using a different browser, or switching devices starts a fresh guest. Encourage players to use the "upgrade to email" flow (Settings) as soon as they care about keeping progress — it converts a guest into a full account without losing coins, gems, level or inventory.

Is there an admin panel?

Not in v1.0. All tuning is done directly against the database — see Economy & Tuning for the full list of tables/keys and which ones need a rebuild vs. a plain UPDATE.

Open a support ticket from the item page on CodeCanyon with: the exact command/step that failed, the full error output, your Node version (node -v), and whether it's local dev or a production deploy.
